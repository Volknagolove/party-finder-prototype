# Интеграция Party Finder

## Граница данных

Публичная страница и интерфейс ЛК — два клиента одного Party Finder API. Общая база хранит `parties`, `party_members`, `vacancies`, `applications`, `sessions`. Лидер занимает одно из девяти мест в `party_members`; остальные уже собранные игроки находятся там же. Вакансии хранятся отдельно. Принятая заявка занимает вакансию через `accepted_slot`, но остаётся в истории откликов; индекс вакансии нельзя удалять, пока принятого игрока не исключили.

Контакты лидера не возвращаются в публичном списке и поиске. После подачи заявки они доступны её отправителю в ответе и в списке своих откликов; владелец объявления видит собственные контакты. Контакты кандидата сохраняются с откликом и возвращаются только отправителю и владельцу объявления. Бейдж «Авторизован» относится к способу подтверждения персонажа, а не к праву смотреть объявления или подавать отклик.

## API прототипа

Все запросы идут на том же origin, что и страница. Гость использует HttpOnly cookie `pf_guest_session`: 30 дней от создания, с проверкой срока на сервере. Выход из интерфейса сохраняет cookie. Поддерживается только гостевой API; подключение подтверждённого профиля требует серверной интеграции ЛК. Заголовок `X-Party-Access` не является авторизацией. Тело и ответ — JSON. Ошибки имеют вид `{"error":"Сообщение"}`. Базовый путь `/api`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /health` | Проверка сервера |
| `GET /session` | Гостевой режим и признак известной действующей cookie |
| `POST /session/guest`, `DELETE /session` | Начать или продолжить гостевую сессию / выйти из интерфейса с сохранением cookie |
| `GET /bootstrap` | Своё объявление, закрытое объявление для восстановления, свои отклики и кандидаты своего объявления |
| `GET /parties?server=teon` | Активные объявления сервера |
| `POST /parties/search` | Подходящие объявления без контактов лидера |
| `POST /parties`, `PUT /parties/{id}` | Создать / изменить своё объявление |
| `DELETE /parties/{id}`, `POST /parties/{id}/restore` | Закрыть / восстановить |
| `POST /parties/{id}/applications` | Откликнуться |
| `PATCH /applications/{id}` | `accepted`, `declined`, `withdrawn`, `removed` |

Пример поиска:

```json
{
  "serverId": "teon",
  "className": "Treasure Hunter",
  "level": 77,
  "timeZone": "Europe/Madrid",
  "availability": [[19,20,21],[19,20,21],[19,20,21],[19,20,21],[19,20,21],[19,20,21],[19,20,21]]
}
```

Массив расписания начинается с понедельника, каждый вложенный массив содержит часы начала одночасовых слотов (0–23) в указанной зоне IANA. В ответе `parties[]` есть `members[]`, `vacancies[]`, `authStatus`, `weeklyAvailability`, `timeZone`, `expiresAt`, но нет `contacts`. Контакты лидера возвращаются отправителю только после создания отклика (поле `leaderContacts` в отклике). Расписание пати должно **целиком** помещаться в доступные часы кандидата. Поэтому пати может играть меньше, но не больше времени, чем он указал. В реальном сервисе лучше закрепить семантику повторяющихся часов и перехода на летнее время в отдельном тестируемом модуле.

Пример создания объявления: `name`, `serverId`, `leaderCharacterId` для ЛК **или** `leaderName`/`leaderClass`/`leaderLevel` для гостя, `contacts:{telegram,discord}` (хотя бы один), `timeZone`, `weeklyAvailability`, `members:[{name,className}]`, `vacancies:[{className,minLevel,maxLevel}]`. Вместе с лидером не больше девяти мест; хотя бы одна вакансия обязательна. Сервер сам назначает срок `createdAt + 7 суток` и проверяет владельца при изменении.

Пример отклика: `characterId` для ЛК **или** `characterName`/`className`/`level` для гостя, `availability`, `timeZone`, `contacts:{telegram,discord}` (хотя бы один). Сервер повторно проверяет все требования. Он же назначает статус и подтверждённость; присланный клиентом `authStatus` игнорируется. Если новый отклик поступил в последние 24 часа действия пользовательского объявления, срок увеличивается на 24 часа.

## Подключение реального ЛК

1. Встроить API в инфраструктуру ElmoreLab или поднять отдельный Party Finder сервис с общей БД. Не давать браузеру прямого доступа к БД.
2. ЛК передаёт на backend проверенную сессию. Backend сам получает аккаунт, сервер и персонажа из существующего профиля; не доверяет присланным из браузера имени, классу и уровню. Для гостя эти поля остаются ручными и помечаются `guest`.
3. Публичный сайт вызывает тот же API поиска. Ему не нужна сессия профиля для просмотра и отклика. Если публичное создание/отклики должны переживать очистку cookie, нужен отдельный механизм восстановления владения (например, одноразовый секрет или ссылка на подтверждённый контакт).
4. Для обновления уровня подтверждённого лидера и кандидатов использовать профильный сервис при чтении с кэшем или фоновую синхронизацию. Гостевые уровни не обновлять автоматически. Исторические заявки должны сохранять данные на момент подачи отдельно от текущих показателей персонажа.
5. Перенести схему в выбранную production-СУБД, добавить миграции, транзакции при конкурирующем приёме на одно место, индексы, журналирование, политики хранения/удаления контактов и модерацию.

Тестовые шаблоны удалены. Новая база создаётся пустой. Проверки API используют отдельную базу в памяти и не заполняют рабочую базу.


## Лимиты и сроки

Объявления и заявки сохраняют IP соединения, присланным IP из JSON и X-Forwarded-For API не доверяет. В production за reverse proxy потребуется доверенная настройка реального IP. Нельзя просто проксировать весь трафик как один IP: все пользователи будут делить лимиты прокси.

`GET /bootstrap` возвращает `listings[]` — все свои объявления — и прежнее `listing` для совместимости. До 5 активных пати на cookie и на IP, включая восстановленные. Редактирование действующей пати не расходует дополнительное место. Персонаж поиска — сервер + ник без регистра; одновременно до 5 таких персонажей с `pending`, один персонаж может откликаться в разные пати без ограничения числа активных откликов.

У отклика есть `expiresAt` (7 суток от `createdAt`); эффективный статус `expired` возвращается для просроченного `pending`. Истечение не затрагивает `accepted`. Отозванные/отклонённые/принятые/истёкшие заявки не входят в лимит ожидающих персонажей. Обход лимитов через одновременные изменения предотвращается транзакцией SQLite `BEGIN IMMEDIATE`.


Защита повторной подачи: один персонаж в одну пати — пауза 1 минута от предыдущего `createdAt`, по владельцу либо IP. Независимые пати не ограничиваются этой паузой. HTTP 429 содержит объяснение.

Постраничная история в `/bootstrap`: `?limit=50&offset=0`, ответ содержит `applicationsHasMore` и `applicationsNextOffset`. Принятые игроки активных своих пати добавляются вне страницы для управления составом. Архив закрытых/давно истёкших заявок очищается спустя 90 дней порциями; `accepted` не удаляются этой очисткой.

Если IANA-пояс не распознан, используется `Europe/Kyiv`. Расписание хранится исходными локальными часами с IANA-поясом, сравнение интервалов выполняется по UTC-минутам; интерфейс переводит и отображает минуты. Чтение и разбор тела HTTP выполняются до транзакции БД, коммит — до отправки ответа клиенту.


## Развёртывание за прокси

Python продолжает слушать только 127.0.0.1. HTTPS завершает обратный прокси, сертификат настраивается на сервере размещения. Задайте `PARTY_FINDER_HOSTS` именами фактических доменов и `PARTY_FINDER_TRUSTED_PROXIES` точными адресами/CIDR прокси (например, `127.0.0.1/32` для локального nginx). Прокси передаёт исходный Host, устанавливает X-Forwarded-Proto и корректно дополняет X-Forwarded-For адресом соединения. Без списка доверенных прокси эти заголовки игнорируются.

При доверенном HTTPS API выдаёт Secure-cookie и HSTS, запрещает Origin с другой схемой или хостом. Не включайте в список доверенных прокси сети обычных посетителей. Если несколько процессов обслуживают API, лимиты частоты запросов нужно вынести из памяти процесса в общий сервис; ограничения активных записей уже проверяются в общей БД.

Параметры пагинации: limit 1–100, offset 0–10000, без дублирования. Непредставимый в UTF-8 Unicode и слишком сложный JSON дают 400. Поиск выполняет SQL-фильтрацию доступных вакансий до преобразования расписаний; расписание кандидата преобразуется один раз, повторяющиеся расписания пати кэшируются в пределах запроса.
