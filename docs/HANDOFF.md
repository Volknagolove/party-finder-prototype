# Передача Party Finder разработчику ElmoreLab

## Что передаётся

Репозиторий содержит две версии интерфейса Party Finder: публичную для гостя и оформление внутри ЛК (поиск пати и создание объявления, светлая и тёмная темы). Обе версии задуманы как клиенты одного Party Finder API и общей базы объявлений, состава, вакансий и заявок. Локальный Python/SQLite-сервер — проверяемый прототип, а не готовый production-сервис.

Запуск и тесты описаны в [README.md](../README.md), текущие запросы и правила доступа — в [INTEGRATION.md](INTEGRATION.md), таблицы прототипа — в [schema.sql](../schema.sql). Использовать эти файлы как описание существующего поведения, а не как требование сохранить SQLite или Python в production.

## Что пока не подключено

- В `server.py` действуют только гостевые cookie-сессии. Реальная сессия `profile.elmorelab.com` не проверяется, персонажи аккаунта не загружаются. Заголовок `X-Party-Access` и параметр URL `view=cabinet` не являются авторизацией.
- `app.js` показывает оболочку ЛК лишь при прежнем тестовом статусе `demo`; рабочий API этот статус не выдаёт. Массив `profileCharacters` сейчас пуст. Сам интерфейс ЛК сохранён в `party-finder/index.html`, `cabinet.js` и `cabinet.css`.
- Опубликованный репозиторий не включает локальную SQLite-базу и не должен содержать реальные учётные данные или игровые данные.

## Задача интеграции

1. Разместить публичный интерфейс на внешнем сайте, а версию ЛК — внутри существующего авторизованного кабинета. Не считать `view=cabinet`, `sessionStorage` или поле `authStatus` доказательством входа. Переход на официальный вход должен возвращать пользователя в ЛК по согласованному маршруту.
2. Подключить к Party Finder серверную проверку действующей сессии ЛК. Определять неизменяемый ID аккаунта на сервере; загружать список принадлежащих ему персонажей из существующего источника профиля с ID персонажа, сервером, именем, классом и уровнем. Конкретный маршрут и формат этого источника необходимо согласовать с командой ЛК.
3. При создании пати и отправке заявки из ЛК принимать ID выбранного персонажа, но повторно проверять на сервере его принадлежность аккаунту и соответствие серверу. Имя, класс, уровень и подтверждённый бейдж назначать по серверным данным. Для гостя оставить ручной ввод и гостевой бейдж. Права на редактирование, удаление, принятие и отзыв проверять по серверной личности владельца.
4. Хранить объявления и заявки обеих версий в одном хранилище. Различать владельца-гостя (cookie-сессия) и владельца-аккаунт (стабильный ID) без совпадений идентификаторов. Текущие внешние ключи `owner_key → sessions(id)` требуют миграции или отдельной модели владельца до добавления аккаунтов. Хранить стабильный ID подтверждённого персонажа и снимок данных на момент заявки; текущий уровень подтверждённого персонажа обновлять из источника профиля по согласованной политике. Гостевые данные автоматически не обновлять.
5. Предоставить обеим страницам один контракт Party Finder API. Браузер не должен подключаться к базе напрямую. Поскольку внешний сайт и ЛК находятся на разных доменах, согласовать размещение API и cookies: предпочтительно проксировать API под origin каждой страницы к одному сервису, либо отдельно спроектировать CORS, передачу учётных данных и CSRF-защиту. Не расширять область действия cookie профиля без необходимости.
6. Сохранить текущую политику контактов: в результатах поиска контакты лидера скрыты; после подачи заявки они доступны отправителю, а лидер получает контакты кандидата. Не выдавать чужие контакты через общий список или неавторизованный `bootstrap`.

## Проверка перед публикацией

- Гость и пользователь ЛК видят один и тот же список активных объявлений; могут искать, создавать пати и подавать заявки в рамках своих прав. У гостя ручной персонаж, у пользователя ЛК — только принадлежащие ему персонажи.
- Подмена ID персонажа, `authStatus`, `view=cabinet`, cookie или заголовка клиента не позволяет получить бейдж, чужие объявления, заявки и контакты.
- Редактирование/закрытие объявления и обработка кандидатов доступны только владельцу; принятый кандидат занимает вакансию и отражается в составе и поиске.
- Светлая и тёмная темы ЛК, публичная версия, мобильная ширина, сроки объявлений/заявок, часовые пояса и лимиты проверены после интеграции.
- До production отдельно закрыты вопросы HTTPS, CSRF и защиты от спама, миграций и резервного копирования БД, хранения/удаления контактов, прав на сторонние ресурсы в `assets/` и нагрузочной проверки. Текущий локальный сервер нельзя публиковать без этой работы.
